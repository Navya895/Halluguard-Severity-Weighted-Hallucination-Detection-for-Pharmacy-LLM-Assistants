# HalluGuard directory guide

Inspected: 16 October 2026.

Update: `fiinetune_roberta_v3.py` was subsequently revised for grouped validation,
class balancing and isolated training outputs. See [TRAINING_V3.md](TRAINING_V3.md)
for its current workflow; historical training details below describe the original
directory inspection where explicitly noted.

## 1. What this project does

HalluGuard is an academic prototype for examining hallucinations in medical and pharmacy answers. It generates an answer using BioMistral through a local Ollama server, splits the answer into sentence-level claims, and scores those claims using a classifier. The newer interface also assigns a rule-based review priority and optionally measures how similar several generated answers are.

This directory contains application code, data preparation scripts, training experiments, evaluation scripts, annotation sheets, saved models, and a local Python environment. Most implementation lives directly in the project root; the `detector/` and `correction/` folders are currently placeholders.

Scope: Python source was inspected along with configuration, dataset schemas/counts, and the file inventory. Model weights, pickle objects, the PDF report, and image contents were not interpreted. Third-party code inside `.venv/` and generated bytecode are summarized rather than documented file by file. This guide describes static code and existing artifacts; it does not claim that training or inference was rerun.

## 2. Main application flow

```text
User question ──> llm_connector.py ──> local Ollama / BioMistral
                                              |
                                        generated answer
                                              |
                                     claim_extraction.py
                                              |
                                       sentence claims
                                              |
Question + supplied reference ──> app_v2.py classifier
                                              |
                             roberta-halluguard-evidence-v2/
                                              |
                         supported / unsupported probabilities
                                              |
                              keyword-based review priority
                                              |
                                     Streamlit results

Optional: three extra answers ──> MiniLM embeddings ──> similarity instability
```

`app_v2.py` is the evidence-aware interface. `app.py` is the earlier frozen-encoder/logistic-regression interface. Neither interface automatically calls `retrieve.py`; reference evidence is entered manually, with the question used as fallback context.

The training convention is **1 = supported / not hallucinated**, **0 = unsupported or hallucinated**, with contradicted examples included in class 0. Unsupported and factually false are not identical concepts. The app presents experimental model outputs, not established factual or clinical certainty.

## 3. Application and shared modules

| File | Purpose and connections |
| --- | --- |
| `app_v2.py` | Streamlit interface using local `roberta-halluguard-evidence-v2`. Combines question and reference, tokenizes context first and claim second with a 512-token limit, and flags claims when P(supported) is below 0.10. Implements its own severity and optional response-stability functions. Includes handling for generation/scoring failures and empty claim extraction. |
| `app.py` | Earlier Streamlit UI. Uses cached `roberta-base` embeddings and `trained_classifier.pkl`, a 256-token limit, and a 0.5 decision threshold. Uses the supplied reference alone as context, or the question if absent. |
| `llm_connector.py` | Requests-based Ollama client. Sends prompts to `http://localhost:11434/api/generate`; lists available models through `/api/tags`. Default model is `m/biomistral:latest`. Used by the apps and LLM severity scorer. |
| `llm.py` | Alternative generation wrapper using the Python `ollama` package and `ollama.chat()`. Reads `MODEL_NAME` from `config.py`. The two Streamlit apps instead use `llm_connector.py`. |
| `config.py` | Defines the alternative wrapper's model name plus application name, version and author metadata. It is not a central configuration source for all scripts. |
| `claim_extraction.py` | Loads spaCy `en_core_web_sm` and returns sentences longer than ten characters. This is sentence segmentation, not a dedicated atomic-claim extraction model. |
| `detector_v2.py` | Reusable fine-tuned detector loading `roberta-halluguard-final`, returning P(class 1) with a 256-token input limit. Used by `run_demo_v2.py`; despite its name, it is not the model loader used by `app_v2.py`. |
| `semantic_entropy.py` | Standalone helper generating multiple answers and returning one minus average pairwise cosine similarity of MiniLM embeddings. This is a response-instability proxy, not a full semantic-entropy estimator. |
| `severity_scorer.py` | Rule-based severity helper. Multiplies hallucination probability by keyword risk weight (1.0, 0.65 or 0.3), then assigns LOW, MEDIUM, HIGH or CRITICAL. |
| `severity_scorer_llm.py` | Asks BioMistral to classify potential severity if a claim were false. Parses one of four tiers, falling back to MEDIUM if parsing fails. |
| `retrieve.py` | Lazily loads `retrieval_index.pkl` and MiniLM. Retrieves the most similar evidence passages by cosine similarity; returns passages and scores. Standalone capability, not wired into either UI. |

In `app_v2.py`, review priority equals P(unsupported) multiplied by keyword risk weight. Tier boundaries are 0.20, 0.45 and 0.70. Its keyword matching and function signature differ from `severity_scorer.py`, so the two implementations should not be treated as interchangeable.

## 4. Dataset creation and annotation

| Script | Reads / source | Produces / purpose |
| --- | --- | --- |
| `load_data.py` | Hugging Face `UTAustin-AIHealth/MedHallu`, configuration `pqa_labeled` | Loads the train split and prints an example when run directly. |
| `build_pairs.py` | MedHallu | Filters pharmacy-related rows, creates true/false answer pairs with question-only context, shuffles and splits 80/20 into `train_val_pairs.json`. Uses full data if the filtered set is too small. |
| `build_pairs_v2.py` | MedHallu | Adds Knowledge evidence to the question; creates a seeded 80/20 split in `train_val_pairs_v2.json`. |
| `build_pairs_v3.py` | MedHallu + `train_val_pairs.json` | Adds evidence while preserving the original claim split; writes `train_val_pairs_v3.json`. Unmatched claims are skipped. |
| `build_pharmacy_dataset.py` | `pharmacy_dataset.csv` or `pharmacy_dataset_annotated.csv` | Chooses the candidate with the most complete non-example records, validates fields/IDs, creates true/false pairs, and holds out entire drugs for `pharmacy_train.json` and `pharmacy_test.json`. It does not automatically verify medical truth or annotation status. |
| `build_retrieval_index.py` | MedHallu Knowledge passages + MiniLM | Writes passages, questions and embeddings to `retrieval_index.pkl`. |
| `build_severity_labeling_set.py` | Original train/validation pairs + `test_set.json` | Samples 50 claims and adds the eight test responses to create `severity_labeling_sheet.csv`. |
| `merge_severity_labels.py` | `label_navya.csv`, `label_reshma.csv`, `label_vedika.csv` | Reports agreement and writes majority labels to `severity_labels_final.csv`. Three-way disagreements are printed but still receive a first-encountered vote until manually resolved. |

The original MedHallu builders split individual pairs, not groups of source questions. The v3 builder preserves that existing split; it does not introduce a question-held-out split.

Pair datasets use this structure (text below is illustrative):

```json
{"claim": "Statement being assessed", "context": "Question and evidence", "label": 1}
```

The MedHallu pair files wrap lists under `train` and `val`; the pharmacy train/test files are separate top-level lists.

## 5. Training scripts and saved models

| Script | Training input | Output |
| --- | --- | --- |
| `train_classifier.py` | `train_val_pairs.json`; frozen RoBERTa embeddings, length 256 | Logistic regression in `trained_classifier.pkl`. |
| `train_classifier_v2.py` | `train_val_pairs_v2.json`; frozen RoBERTa embeddings, length 512 | Logistic regression in `trained_classifier_v2.pkl`. |
| `finetune_roberta.py` | `train_val_pairs.json`; full RoBERTa fine-tuning, four epochs, length 256 | Checkpoints in `roberta-halluguard-finetuned/`; selected export in `roberta-halluguard-final/`. |
| `finetune_roberta_v2.py` | `train_val_pairs_v3.json`; evidence-aware fine-tuning, four epochs, length 512 | Checkpoints in `roberta-halluguard-evidence-checkpoints/`; export in `roberta-halluguard-evidence/`. |
| `fiinetune_roberta_v3.py` | Rebuilds context/claim-grouped splits from `train_val_pairs_v3.json`; adds configurable mismatch negatives and balanced loss | Saves model, checkpoints and evaluation artifacts in a separate `training_runs/evidence-v3-<timestamp>/` directory. See `TRAINING_V3.md`. |
| `calibirate.py` | Validation examples from `train_val_pairs.json` and `roberta-halluguard-final/` | Optimizes a temperature scalar with validation logits and saves `temperature.json`. |

The exact filenames really are `fiinetune_roberta_v3.py` and `calibirate.py`, including their spelling.

## 6. Evaluation and diagnostics

| File | What it checks |
| --- | --- |
| `run_demo.py` | Evaluates the original logistic-regression detector against `test_set.json`, averaging extracted claim scores per response. |
| `run_demo_v2.py` | Similar evaluation using `detector_v2.py` and `roberta-halluguard-final/`. |
| `compare_model_on_testset.py` | Compares question-only and evidence-v2 models on the eight response-level examples. |
| `compare_pharmacy_model.py` | Compares the final and evidence-v2 models on `pharmacy_test.json`, printing probabilities and accuracy. |
| `eval_zero_shot.py` | Uses existing evidence-v2 weights, selects a threshold on `pharmacy_train.json` by balanced accuracy, evaluates the held-out pharmacy test set, prints error analysis, and saves `detector_evaluation_results.json`. It does not train weights; threshold selection still uses labeled examples. |
| `evidence_shuffle_test.py` | Tests correct evidence, a single deterministic mismatched-evidence shuffle, and claim-only input on v3 validation pairs. |
| `check_evidence.py` | More extensive evidence-sensitivity diagnostic using five seeded shuffles, bounded attempts to avoid original contexts, and several metrics. Its internal header names the older shuffle script, but this file is `check_evidence.py`. |
| `threshold_analysis.py` | Sweeps thresholds from 0.10 through 0.60 on the v3 validation split using evidence-v2 weights. |
| `check_length.py` | Measures context token lengths for the first 100 v2 training examples. |
| `validate_semantic_scorer.py` | Despite its filename, evaluates the rule-based **severity** scorer against consensus labels, using fixed hallucination probability 0.7. |
| `validate_severity_llm.py` | Compares BioMistral severity predictions with consensus labels. |
| `pytorch_test.py` | Prints CUDA availability, GPU count/name and PyTorch CUDA version. |

These are executable research/diagnostic scripts rather than a conventional isolated unit-test suite. Many run model loading or other work at module import time.

## 8. How to navigate or run the project

For understanding the live application, read `app_v2.py`, then `llm_connector.py`, then `claim_extraction.py`. For model history, follow the training table. For the pharmacy evaluation workflow, read `build_pharmacy_dataset.py` and `eval_zero_shot.py`.

From the project root, the existing environment can launch the newer interface with:

```powershell
.\.venv\Scripts\python.exe -m streamlit run app_v2.py
```

Prerequisites are the local Ollama service with the exact configured BioMistral model, the local RoBERTa export, Python dependencies, and spaCy's `en_core_web_sm` model. Optional stability scoring also needs cached `all-MiniLM-L6-v2`. The older app additionally needs cached `roberta-base`.

Many scripts explicitly enable Hugging Face/Transformers offline mode. Their datasets and pretrained models must already be cached; this guide does not assume a fresh installation will download them automatically. Paths are generally relative to the working directory, so launch commands from this folder.

Example evaluation commands (these were not executed for this documentation task):

```powershell
.\.venv\Scripts\python.exe eval_zero_shot.py
.\.venv\Scripts\python.exe check_evidence.py
.\.venv\Scripts\python.exe pytorch_test.py
```

`eval_zero_shot.py` rewrites its saved results file. Dataset builders and training scripts also write outputs; they are not necessary merely to launch an app when required artifacts already exist.

## 9. Important implementation details

1. **Newest training script has been revised.** The missing PyTorch import and reused checkpoint directory were fixed. It now selects on macro F1 from grouped original validation examples and reports synthetic mismatches separately. New exports do not automatically replace the app's evidence-v2 model. See `TRAINING_V3.md` for the changed split and validation procedure.
2. **Calibration is not connected to inference.** The current app and detector do not read `temperature.json`; having that artifact does not mean displayed probabilities use temperature scaling.
3. **Dependency configurations differ.** `pyproject.toml` specifies the `cu132` PyTorch index, while `requirements.txt` pins Torch/Torchvision builds marked `cu126`. The alternative `llm.py` imports `ollama`, which is not listed in either dependency declaration. spaCy's language model is also an additional resource.
4. **Evidence retrieval and correction are not part of the live pipeline.** Retrieval is implemented as a standalone helper; correction is an empty module.
5. **Thresholds differ across experiments.** The newer UI uses 0.10, earlier demos typically use 0.5, and pharmacy evaluation selects a threshold from its training split. Their predictions should not be assumed directly comparable without accounting for these differences.
6. **Dataset preparation is structural validation.** The pharmacy builder checks completeness and duplicate IDs, not source reliability or clinical validity. Filling `pharmacy_dataset_template.csv` alone is insufficient because the builder's actual candidate list uses the other two CSV filenames.
